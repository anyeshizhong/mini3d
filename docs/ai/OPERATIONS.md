# Mini3D AI 操作规程（OPERATIONS）

> 版本 0.1。按任务使用，不是每个任务都必须运行全部测试。
> 此文档由 `FIRST.md` 路由。执行权限以用户指令、工作区状态与当前 Agent 可用工具为准。

## 1. 接单、检查与任务分配

1. **主 Agent** 将用户自然语言整理成：目标行为、复现路径、完成标准和暂不涉及的范围。不要让用户替开发团队挑文件。
2. 查看 `git status --short`、`git branch --show-current`、`git log -1 --oneline`，记录现有工作区改动；不自动丢弃。
3. 按 `FIRST.md` 分类，读 `FILE-REGISTER.md` 相关区域，**先找证据再确定负责人**。局部问题由一个模块处理；跨 Scene/Shot/API/native 契约时主 Agent 协调各模块。
4. 先读相关的实现、调用者与测试；有问题不等于立刻重构。若用户给的是可见 Bug，先尽量建立可复现测试。
5. 修改计划应写清路径与理由。不要仅因多人协作就拆出不必要的脚本、类和抽象层。

## 2. Bug 修复 SOP

- 固定场景、输入、相机姿态、渲染后端、画质参数和预期现象；能截图或测量则留基线。
- 查找实际数据流，确认根因所在及上下游接口，避免用背景板、模糊、强雾或关闭功能遮掩。
- 增加或选择能失败于旧实现、通过于新实现的回归检查。
- 修复应以最小**合理**范围改动；一旦影响另一个模块的公共契约，补充联动验证。
- 修复后复跑相同场景和采样，记录结果与未覆盖情况。视觉问题需实际 GL 图像检查，只有 CPU 单测不够。

## 3. 新功能 SOP

- 描述用户操作：入口 → 动作 → 可见反馈 → 保存/撤销/重新打开。
- 优先复用现有 Scene、Commands、Shot、API，不平行建立互不一致的状态。
- 若新增公共能力，明确 UI 与 AI API 是否需要共用，修改相应文档和测试。
- 对导入、存档或跨语言协议修改做兼容性验收；不要悄悄打破已有模型/场景。

## 4. UI / 摄影 / 渲染 / 性能的差异验收

| 任务 | 特别要验收什么 |
| --- | --- |
| UI/编辑器 | 按键与鼠标捕获、跨面板取消、选中状态、撤销重做、重启恢复 |
| Placement | 坐标/锚点、组与实体 ID、事务只占一次 Undo、Scene 保存载入 |
| Photography | Camera View vs PNG 一致、点击真实深度对焦、景深/色彩、1x/4x AA、重载 |
| Python ↔ native | 确认实际后端、bundle 字段与资源同步、GL 状态恢复、资源生命周期 |
| 渲染/阴影 | 真实深度与遮挡、静止和移动镜头、近远阴影、材质/透明回归 |
| 性能 | 同设备/场景/分辨率/AA/阴影配置，区分完整帧、CPU submit 和 GPU 耗时，记录 P50/P95/P99 |

**30 FPS 是底线目标，不是可无条件宣布的现状。** 33.33ms 为单帧时间参考阈值；P95 小于阈值也不等于完全没有长尾卡顿。历史分支、无 UI 查看器、不同 AA 或分辨率的成绩不能混报。

## 5. 现有运行、API 与测试入口

在项目根目录、安装了依赖并具有相应桌面 GL 环境时执行：

```powershell
# 主程序（统一 Editor 入口）
python -B -m mini3d

# 复现 Roman Street
python -B -m mini3d --scene examples/roman_street/street.json

# 单元测试（无需虚报本地执行结果）
python -B -m unittest discover -s tests -p "test_*.py"

# 原生 Shot（构建 DLL 后，强制不允许 Python fallback）
$env:MINI3D_REQUIRE_NATIVE_PHOTO = "1"
python -B -m mini3d --scene examples/pompeii/native-photo.json
```

已有本机环境可使用 `F:/gymenv/python.exe`；换机器必须以实际解释器为准。测试是否有 GPU/资产依赖，须读脚本和对应文档，不要只看名字。
原生构建与后端选项见 `NATIVE-PHOTO.md`、`spqr-native/README.md`，禁用/强制回退细节按当前实现检查。
调用 AI API 前读 `docs/ai-api-v1.md`；从外部操作已打开的编辑器，先读 `docs/live-editor-ipc.md` 和 `docs/ai-view-api.md`，避免另起一个不共享用户场景的 Editor 实例。

## 6. 交付及登记反馈模板

最终交付应简要包含：

- **结果**：解决了什么、如何实际观察；
- **修改范围**：分支、提交、具体脚本，以及跨模块修改理由；
- **验证**：已运行的命令、场景、后端和实际结果；没有运行的测试须明确标识；
- **限制**：未解决的问题、性能/画质和兼容性风险；
- **档案回写**：新脚本的职责、接口变化或新测试入口已更新到何处。

**禁止**：未检查即清理用户数据；把文档说明当成最新实测；借 bug 修复暗中扩大到无关重构；为了“只动一个文件”而牺牲正确性；为了省 Token 省掉必要的验收。
